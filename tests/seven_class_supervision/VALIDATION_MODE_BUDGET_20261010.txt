Implementation and controls
runtime_dataset_probe --mode-budget executes the actual private loader, model,
preprocessing, current loss, decoding and mask functions in the production source
translation unit. Legacy loss is frozen from f89ce6a in a test-only header. Its
body was compared with git show: exact match after renaming the function symbol.
This is not a reimplementation of a Python model and does not execute Python.

Both training arms use the same freshly loaded registered parent, frozen dataset,
CPU, seed 20261010, Adam, batch size 1, 20 epochs / 40 updates, Train sample order,
cosine LR 1e-4 -> 1e-6, weight decay 0 and evaluation cadence. Two Train samples
are visited once each per epoch; the one Valid sample is evaluated without
gradients. VERIFY is excluded from training and validation loss. Class order,
thresholds and NMS are unchanged. No cross-objective loss-value ranking is made.

This common diagnostic loop is not a new business ABI. Its dense-v2 final model
parameters AND buffers exactly reproduce the preceding real C ABI 40-update
trial (max absolute state difference 0, checkpoint SHA also identical). That
check is mandatory and fails the experiment if reproduction differs.

Mode experiment
For each of parent, legacy-v1 and dense-v2, each of four samples is run under:
eval; train; train with every BatchNorm2d module set to eval. 36 forwards total.
Every forward reloads a fresh checkpoint; no optimizer step or gradient is made.
The train forward's local buffer updates are discarded. Models are never saved
after these forwards. There are 66 BatchNorm2d modules per model.
Production DecodeCandidates / DecodeMask / LargestContour filtering is reused.
VERIFY mask oracle is reconstructed only for scoring from the R&D generator;
it is not inserted into the frozen dataset. Scores are best matching accepted
ellipse-instance IoU, not accuracy, precision, recall or duplicate-free success.

Interpretation and limitations
The observed train/eval output difference is attributable to BatchNorm behavior
in these tested models. This does not prove BatchNorm is the only reason dense-v2
misses Train0: ordinary train still has only .559578 IoU, and the revised loss
changes both optimization and the statistics learned along that trajectory.
Switching inference to train is not a remedy: it harms Valid/VERIFY here and makes
results depend on test-image batch statistics. Inference remains eval.
The first dense repair supplies missing background gradients, but its center-only
positive assignment plus treatment of all other anchors as negative needs further
evaluation. The experiment does not independently isolate assignment, loss
normalization and BN-update-policy effects. No general seven-class or business
accuracy claim is supported by four same-generator synthetic images.

Next proposed isolated experiments (not implemented by this diagnostic)
1. Factorial controls for BN training policy and loss version at equal budget;
   keep validation/test images out of any running-statistic recalibration.
2. Coherent task-aligned positive assignment across class/box/DFL/mask, rather
   than relabelling every non-center anchor negative without testing alternatives.
3. Add per-image target counts, false positives and duplicate penalties to the
   quality gate, plus independent shapes before accepting a new default.
Neither legacy nor dense-v2 is approved or automatically selected by this work.
